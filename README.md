# IPTV / HLS restream proxy

Асинхронный HTTP-прокси на `aiohttp`, полностью ретранслирующий HLS-плейлисты
и все связанные ресурсы (сегменты `.ts`/`.m4s`, вложенные вариант-плейлисты,
ключи шифрования, init-сегменты) через себя, переписывая все ссылки на свой
адрес. Клиент никогда не обращается к серверу провайдера напрямую — заголовки
и адрес исходного провайдера от него скрыты. Управление пользователями не
реализуется — доступ открыт всем, кто знает адрес прокси, включая
веб-интерфейс управления провайдерами (`/admin/`, без авторизации).

## Быстрый старт

### Без Docker

```bash
pip install -r requirements.txt
# отредактировать config.py (host_name, порт) - см. "Настройка"
python3 server.py
```

Сервер слушает `0.0.0.0:<port>`, порт берётся из `config.py`. Каналы
добавляются потом через `http://<host_name>:<port>/admin/` — редактировать
`config.py` для этого не нужно (см. "Управление провайдерами").

### С Docker

```bash
cp .env.example .env   # при необходимости поменять порт
# отредактировать config.py (host_name, порт) - см. "Настройка"
docker compose up -d --build
```

`config.py` в образ не встраивается — он монтируется как volume, только для
редко меняющихся параметров (`host_name`, `scheme` и т.п.), правка + рестарт
контейнера без пересборки образа. Провайдеры каналов добавляются через
`/admin/` (см. "Управление провайдерами") — при первом запуске автоматически
переносятся из `config.py`, если они там были. Порт задаётся один раз, в
`.env` (`IPTV_PROXY_PORT`) — подробности см. в разделе "Порт при запуске в
Docker" ниже.

## Настройка

Деплой-параметры — в `config.py`:

```python
port = 1200
host_name = 'mydomain.com'
```

| Параметр | Назначение |
|---|---|
| `port` | Порт сервера (без Docker). При запуске в Docker переопределяется `IPTV_PROXY_PORT`, см. ниже. |
| `host_name` | Домен/IP, который клиенты используют для обращения к прокси — именно он подставляется во все переписанные ссылки. Должен быть реально доступен клиентам, не «внутренний» docker-хостнейм. |
| `scheme` | `http`/`https` — схема в переписанных ссылках, см. "Если нужен HTTPS". |
| `user_agent`, `connect_timeout`, `read_timeout` | Опциональны, есть разумные значения по умолчанию. |
| `provider` | Используется **только один раз**, при самом первом запуске, как начальные данные — см. "Управление провайдерами" ниже. |

## Управление провайдерами через веб

Список провайдеров (каналов) хранится не в `config.py`, а в
`data/providers.json` и управляется через `http://<host_name>:<port>/admin/`:

- таблица текущих провайдеров (ключ, URL, наличие доп. заголовков), для
  каждого — ссылка на публичный плейлист, "Изменить" и "Удалить";
- форма добавления/изменения: ключ (латиница/цифры/`-`/`_`, используется как
  `/<ключ>/`), URL плейлиста, и опционально доп. заголовки (по одному на
  строку, `Имя: значение`) — например `Referer`, если провайдер его
  проверяет.

Изменения через `/admin/` применяются **сразу**, без перезапуска процесса.
`data/providers.json` можно так же редактировать вручную (это обычный JSON)
— такие правки, как и раньше правки `config.py`, применяются только после
перезапуска процесса/контейнера.

При самом первом запуске, если `data/providers.json` ещё не существует, он
автоматически создаётся и заполняется из `provider = {...}` в `config.py`
(если там что-то было) — так уже настроенные провайдеры не теряются при
переходе на веб-управление. После этого `config.py`-шный `provider` больше
не читается.

**Без авторизации.** `/admin/` не защищён — как и весь сервис, по условию
задачи. Любой, кто может достучаться до порта прокси, может
просматривать/добавлять/менять/удалять провайдеров, включая URL с токенами
в заголовках. Если прокси выставлен в открытый интернет, а не только в
локальную сеть — ограничивайте доступ на уровне файрвола/реверс-прокси
(например, разрешайте `/admin/` только с доверенных IP) — это вне зоны
ответственности самого сервиса.

### Порт при запуске в Docker

Порт указывается **один раз** — в `.env` (`IPTV_PROXY_PORT`), а не отдельно
в `config.py` и `docker-compose.yml`. Сервер при старте проверяет переменную
окружения `IPTV_PROXY_PORT`; если она задана — использует её вместо `port` из
`config.py` сразу в трёх местах: bind-порт сервера, порт, зашиваемый в ссылки
плейлиста (`host_name:port`), и порт, публикуемый наружу контейнера
(`docker-compose.yml` берёт ту же переменную для `ports:`). Без Docker
переменная не установлена, и порт берётся из `config.py`, как раньше.

Это специально сделано так, чтобы исключить типичную ошибку при
доккеризации прокси: наружу опубликован один порт, а в плейлисте, который
получает клиент, зашит другой (недоступный снаружи контейнера) — плеер в
этом случае не сможет подключиться ни к одному сегменту.

## Использование

- `http://mydomain.com:1200/one/` — плейлист провайдера `one`, все ссылки
  внутри (сегменты, вложенные плейлисты, ключи) переписаны на прокси.
- `http://mydomain.com:1200/one.m3u8`, `http://mydomain.com:1200/one/playlist.m3u8`
  — алиасы того же самого плейлиста с расширением в адресе. Нужны для
  IPTV-приложений (в том числе на Smart TV — Samsung Smart IPTV/SS IPTV),
  которые жёстко требуют `.m3u`/`.m3u8` в URL и не принимают адрес без
  расширения.
- `http://mydomain.com:1200/` — служебная страница со списком каналов.
- `http://mydomain.com:1200/admin/` — управление провайдерами (см. выше).

Прокси одинаково хорошо работает как с простыми медиаплейлистами (список
сегментов), так и с мастер-плейлистами (несколько вариантов битрейта) —
вложенные плейлисты рекурсивно скачиваются и переписываются точно так же.
Поддерживаются одновременные подключения нескольких клиентов (см.
"Возможные проблемы" насчёт лимитов провайдера).

## Как это устроено

- `GET /<key>/` — сервер скачивает исходный плейлист провайдера с ключом
  `key` (см. `providers_store.py`), построчно проходит по нему и заменяет:
  - обычные строки-ссылки (сегменты, вложенные `.m3u8`);
  - `URI="..."` внутри тегов `#EXT-X-KEY`, `#EXT-X-MAP`, `#EXT-X-MEDIA`,
    `#EXT-X-I-FRAME-STREAM-INF` и т.п.

  Относительные ссылки резолвятся относительно URL исходного плейлиста
  (`urljoin`), после чего оборачиваются в ссылку вида
  `http://mydomain.com:1200/<key>/res/<token>.<ext>`, где `<token>` —
  base64url-кодированный исходный абсолютный URL.

  Ответ считается плейлистом не по `Content-Type` от провайдера (он часто
  врёт — см. "Возможные проблемы"), а по содержимому: если тело реально
  начинается с `#EXTM3U`. Дальше сервер сам определяет, что перед ним:
  настоящий HLS-плейлист (есть `#EXT-X-TARGETDURATION`/`#EXT-X-STREAM-INF` и
  т.п. — тогда отдаётся `Content-Type: application/vnd.apple.mpegurl`) или
  обычный M3U-список каналов, где каждая ссылка ведёт на отдельный поток
  (тогда — `audio/x-mpegurl`, чтобы плеер не пытался разобрать список как
  живой HLS-поток).

- `GET /<key>/res/<token>` — декодирует исходный URL из токена и:
  - если это плейлист (по расширению `.m3u8`/`.m3u` либо по
    `Content-Type: ...mpegurl`) — рекурсивно скачивает и переписывает так же,
    как корневой плейлист;
  - иначе — стримит содержимое (сегмент, ключ и т.д.) клиенту байт в байт,
    без буферизации в памяти, с проксированием заголовка `Range` для
    поддержки перемотки.

- `providers_store.py` — отдельный модуль, хранящий провайдеров в
  `data/providers.json` (атомарная запись через временный файл + `os.replace`,
  под `asyncio.Lock`). `server.py` обращается к нему как через `/admin/`
  (веб-хендлеры), так и при проксировании (`get_provider_entry()`).

## Возможные проблемы

**Провайдер отдаёт плейлист с неверным/generic `Content-Type`
(`application/octet-stream`, `Content-Disposition: attachment` и т.п.).**
Не проблема — сервер сам заглядывает в тело ответа и проверяет `#EXTM3U`,
не полагаясь на заголовки провайдера.

**Провайдер требует свой `User-Agent`/`Referer`/токен.** Задайте
дополнительные заголовки в форме `/admin/` (поле "Дополнительные заголовки",
по одному на строку — `Referer: https://provide.two/`). Если заголовки не
заданы и провайдер не отвечает валидным m3u8 на корневой запрос, сервер
вернёт `502` с диагностикой (URL, статус, `Content-Type`, первые байты
ответа в hex) — этого обычно достаточно, чтобы понять причину.

**Плейлист не воспроизводится в плеере (VLC, Smart TV и т.п.), хотя по HTTP
всё выглядит нормально.** Проверьте `Content-Type` ответа: `curl -v` в
PowerShell на Windows — это алиас на `Invoke-WebRequest`, а не настоящий
`curl`, и он не показывает тело ответа при `-v`/`-Verbose` — тестируйте либо
реальным `curl` (например, из Git Bash/WSL), либо `curl.exe` явно. Если
`Content-Type` внезапно не совпадает с ожидаемым — см. пункт выше про
классификацию плейлиста; для нестандартных провайдеров (плейлист без единого
`#EXT-X-...` тега, но при этом являющийся настоящим одиночным HLS-потоком)
эвристика может ошибочно определить его как "список каналов" — в этом
случае сообщите, поправим классификацию.

**Второй/третий зритель не может смотреть тот же канал (или всех выбивает).**
Прокси не кэширует и не «шарит» поток между клиентами — каждый клиент,
включая тех, кто смотрит один и тот же канал, порождает свой отдельный
upstream-запрос к провайдеру на каждый плейлист и каждый сегмент. Если
подписка у провайдера ограничивает число одновременных соединений (частый
случай у реселлерских IPTV-панелей), N зрителей одного канала = N соединений
у провайдера, и лимит выбивается быстрее, чем кажется. Это ограничение
провайдера, не прокси; если понадобится — можно доработать прокси так,
чтобы N зрителей одного канала расходовали 1 upstream-соединение.

**Много зрителей одновременно (десятки+).** У `aiohttp.ClientSession` по
умолчанию лимит в 100 одновременных соединений на процесс
(`TCPConnector(limit=100)`). Для небольшого числа зрителей это не проблема;
при существенном росте стоит явно поднять лимит в коде.

**После `docker compose up` контейнер падает или плейлист не находится.**
Убедитесь, что `config.py` реально существует рядом с `docker-compose.yml`
*до* первого запуска — Docker может смонтировать несуществующий файл как
пустую директорию вместо ошибки, и импорт `config.py` внутри контейнера
упадёт (для `data/` эта проблема не актуальна — это директория, а не файл,
Docker создаёт её сам при отсутствии). Также проверьте, что
`IPTV_PROXY_PORT` в `.env` совпадает с портом, на который вы реально
стучитесь снаружи.

**Добавил провайдера через `/admin/`, а через минуту его нет.** Проверьте,
не редактирует ли что-то ещё параллельно `data/providers.json` вручную —
запись через `/admin/` перезаписывает файл целиком под блокировкой, но
ручная правка "мимо" процесса применится только после рестарта и может
затереть то, что было добавлено через веб-интерфейс, если основана на
устаревшей копии файла.

**Плейлист отдаётся, но по `http://<host>:<port>/one/` браузер не
показывает его "красиво", а скачивает файл.** Это нормально — браузеры не
умеют рендерить `audio/x-mpegurl`/`application/vnd.apple.mpegurl` и либо
скачивают файл, либо показывают как текст. Так же вело бы себя и прямое
обращение к провайдеру. Не признак проблемы.

**Нужен HTTPS.** Сам прокси отдаёт только HTTP, см. раздел ниже.

## Запуск как systemd-сервис (пример)

```ini
[Unit]
Description=IPTV HLS restream proxy
After=network.target

[Service]
WorkingDirectory=/opt/iptv-proxy
ExecStart=/usr/bin/python3 /opt/iptv-proxy/server.py
Restart=on-failure
User=iptv

[Install]
WantedBy=multi-user.target
```

## Если нужен HTTPS

Сам прокси отдаёт только HTTP. Для HTTPS поставьте перед ним nginx с
терминацией SSL, проксируя на `127.0.0.1:<port>`, и укажите в `config.py`:

```python
scheme = 'https'
```

— тогда ссылки внутри плейлистов будут формироваться с `https://`, при этом
сам процесс `server.py` продолжает слушать обычный `http` локально.
